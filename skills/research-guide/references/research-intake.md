# Start from the Researcher's Situation

Let the researcher begin in ordinary language: what has already been done, what was observed, and what they want to do next. Accept rough notes, figures, papers, or an incomplete explanation. Do not demand a long form before helping.

First use [task-routing.md](task-routing.md) to identify whether the user wants learning, paper analysis, or a full research project. This intake supports that route and is not an extra approval gate. Show a concise reconstruction for correction while continuing useful work within the requested scope.

## Reconstruct the project brief

Use supplied context and accessible records before asking questions. Separate:

| Item | What to capture |
|---|---|
| Completed work | Actual experiments, calculations, analyses, or reading, with conditions and available artifacts |
| Observations | What the data or sources show, separately from the proposed explanation |
| Interpretations | Current hypotheses, assumptions, and competing explanations |
| Desired outcome | What the researcher wants to understand, demonstrate, improve, or decide |
| Current obstacle | The specific uncertainty or missing capability preventing that outcome |
| Resources | Confirmed materials, data, equipment, expertise, time, and access; unknowns remain unknown |
| Prior work | Known papers and protocols, what was actually read, and the closest existing answer if verified |
| Next decision | The decision that a useful answer would change |

Label statements as user-reported, supported by an inspected artifact, inferred, planned, or unknown. A user's account of a measurement is useful context but is not an independent inspection of the underlying data. Do not turn an intended experiment into completed work or infer exact parameters from a qualitative description.

Ask only for missing details that change the next decision, grouping a few closely related points into one question when useful. Summarize what can already be concluded and what needs verification. Do not invent missing background to fill the brief.

## Enter the right scope without restarting the science

A request only to analyze local/online literature goes directly to `research-papers`; do not require selection of a new research direction. Ask for the local folder path if needed. For field learning or project planning, use a short referenced orientation and applied understanding checks from `research-foundations` to adapt depth. Existing work can demonstrate understanding; do not demand repeated tests or make a quiz a prerequisite for paper inventory.

If the researcher already has a specific system, subfield, or question, use it as the starting scope. Do not force a broad ranking exercise merely because this is a new chat. Reuse verified earlier acceptance; otherwise present the existing scope as the concrete stage-1 checkpoint.

Having completed work does not itself accept the subfield, question set, or corpus. Preserve the four-stage gates. A bounded troubleshooting or protocol-reading request can be answered as a standalone helper task when the user asks for that, without falsely marking the larger workflow complete.

## Select a question for deeper reasoning

Choose a bounded question whose answer could change the current plan: conflicting explanations, an unsupported inference, an uncertain experimental transfer, a literature contradiction, or a costly choice between methods. Explain why a separate reasoning pass could help. Routine extraction, simple factual checks, and metadata cleanup do not need another chat.

Use [model-routing.md](model-routing.md) to dispatch an authorized consultation within the current stage, wait for its answer, verify it, and adjust the work. The coordinator prepares the prompt internally. Include both favorable and contrary evidence. If there is not enough context to state a useful question, gather it in the current chat rather than create an empty consultation. A better model cannot replace missing data, missing Methods, or user acceptance.

Keep the filled intake, handoff, and research details in the private project records. The reusable skill and public package contain only the method and empty templates.
