# Reasoning checks and optional consultations

Research depth 1/2/3 describes the analysis to deliver. It does not select a model, product or new chat. Default to the current task. Do not copy a preferred model or automatic-chat instruction from an old public template into a new request.

## Bounded checks within this task

Use a subagent when an independent evidence check, competing explanation or feasibility analysis would help and tools permit delegation. Give it the bounded question, source artifacts, relevant conditions and active-stage limits. Preserve the user's latest verified model choice and apply model-choice-guard before dispatch. Inherit only when the parent model is verified to match; do not substitute another model silently or infer the choice from global defaults or old usage labels. If a required selection is unavailable, hold that affected call and continue useful work that does not depend on it.

Read the returned answer, inspect decisive sources and distinguish observations, authors' interpretations and the agent's inference. Resolve conflicting answers against evidence. Agent agreement is not an independent experiment, a verified citation or user acceptance.

## Separate user-owned chats only when requested

Use supported creation and messaging tools only when the user explicitly requests a separate chat or explicitly authorizes that specific consultation workflow. A skill invocation, depth selection, model preference, project membership or template default is insufficient. Reuse actual authorization within its stated purpose without asking again. Respect a later request to keep work in this chat or prepare a brief only.

When that request exists:

1. State the decision the consultation should resolve and fill the optional [brief](../assets/deep-research-handoff.md) from inspected evidence, relevant contrary evidence, constraints and unresolved facts.
2. Verify the actual destination, project and selected model with available tools. Use an exact model only when the user chose it and it is supported. Do not relabel one product/model as another or infer account access from a missing tool.
3. Reuse an existing consultation for the same question and evidence revision; reconcile an uncertain creation result before retrying. Submit the initial packet once and retain its returned identity.
4. Wait through supported bounded status tools and retrieve the actual complete answer. A creation receipt or elapsed time is not a completed answer. Continue independent work while dependent decisions remain pending.
5. Verify sources, settings and applicability before incorporating recommendations. Record the answer reference, adopted/rejected changes, remaining uncertainties and the revised artifact.

If the selected route cannot be used, explain the concrete capability gap without claiming it ran. Do not automatically switch product, model or browser, create unrelated projects, or require the user to copy a prompt as the normal flow. Follow-up messages remain within the user's actual authorization. Prevent recursive consultations.

## Records and stage boundaries

Keep filled briefs and consultation records outside installed skills. Reuse an existing record format when sufficient. Record the question/evidence revision, authorization source, actual destination and model verification status, returned identity/status, source checks and applied revision. Keep unsupported or unanswered advice provisional.

Preserve all accepted stage versions. A consultation supports the current stage and cannot accept a subfield, questions, library snapshot or review for the user. If verified new evidence materially changes accepted work, reopen only the affected checkpoint and its dependencies.
